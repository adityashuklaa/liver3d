    Run it yourself

    # the whole pipeline on synthetic phantoms, CPU, no dataset needed
python scripts/quickstart.py

# real data
python scripts/build_manifest.py --root data/lits --out data_manifests/split_v1.csv
python -m src.train    --config configs/baseline.yaml
python -m src.evaluate --checkpoint outputs/<run_id>/best.pt --split test

# serve
set LIVER3D_CHECKPOINT=outputs/<run_id>/best.pt
set LIVER3D_API_KEYS=some-long-random-key:clinician
uvicorn src.api.service:app --port 8000

    Every artifact on this screen traces back to one checkpoint bundle: weights, preprocessing config and split manifest travel together, so weights cannot be swapped silently.

    Release
    Preprocessing & inference
    What these numbers prove. The cases here are synthetic CT phantoms generated by the repository, not patient data. They demonstrate that the pipeline is wired correctly end to end — preprocessing inverts, sampling works, inference blends, geometry survives the round trip, the service enforces its roles. They say nothing about clinical accuracy. The source project reported Dice above 0.90 on real data, but no dataset, split, checkpoint or metric export was supplied with it, so that figure stays unverified. Point the config at LiTS or CHAOS, lock a patient-level split, and the same commands produce defensible numbers.

    Standing limits

    ScopeLiver against background only. Tumour segmentation is a separate task with separate labels and metrics.
    GeneralisationPerformance on one dataset does not transfer to a new scanner, protocol or population without external validation.
    ReadingA high Dice can still hide a boundary error that matters clinically. Worst cases get reviewed, not just the mean.
    StatusResearch prototype. Not a cleared medical device; not for patient care without institutional, clinical and regulatory approval.
